# Общие напоминания

Issue #10 добавляет небольшой shared-reminder режим поверх существующей
персональной модели. Напоминание остаётся принадлежащим одному `User` и по
умолчанию приватным. Общим оно становится только после явного принятия
одноразовой ссылки-приглашения.

## Версия v1

Чтобы не смешивать ещё не определённые контракты persistent и deadline режимов,
в v1 можно делиться только активным обычным одноразовым напоминанием:

- `kind=ordinary`;
- `mode=normal`;
- без recurrence и snooze-child;
- завершённые, отменённые, failed и обрабатываемые reminders не принимаются.

Это безопасное ограничение обратимо: будущий Issue может определить отдельные
семантики повторов, дедлайна, quiet hours, acknowledgement и эскалации для
участников, не меняя текущие личные reminders.

## Приглашения и роли

Владелец использует `/share ID`. Бот сохраняет только SHA-256 hash случайного
токена и отправляет владельцу Telegram deep link `/start sr_<token>`. Токен
одноразовый, действует 24 часа, не попадает в логи и может быть отозван до
принятия через `/shared`. Один reminder ограничен пятью активными участниками
и пятью pending invitations.

Принятие ссылки атомарно создаёт `participant` membership. Повторное нажатие
тем же пользователем безопасно идемпотентно; ссылка, принятая другим
пользователем, истёкшая или отозванная ссылка отклоняется. Отзыв membership
повышает его revision и инвалидирует незавершённые fan-out rows, поэтому старые
callbacks не возвращают доступ после повторного приглашения.

Участник может только выполнить или отложить текущий доставленный occurrence.
Владелец сохраняет существующие права редактирования и удаления. Каждая
операция повторно проверяет membership/role, reminder, occurrence, revision,
текущее состояние и (для delivery message) конкретный per-recipient message id
в PostgreSQL-транзакции.

## Доставка и приватность

Доставка идёт в личный чат каждого активного участника, а не в общий Telegram
чат. Владелец всегда является одним из получателей; fan-out ограничен пятью
участниками и хранится в `reminder_deliveries`. Уникальная комбинация
`occurrence + recipient + membership revision` позволяет после restart пропускать
уже подтверждённые отправки и не дублировать их при обычном retry. Граница
Telegram API остаётся стандартной at-least-once границей существующего worker:
если процесс погибает ровно после внешней отправки и до записи результата, может
потребоваться повторная доставка.

Контент самого reminder виден только после принятия приглашения. Сохранённый
Telegram forwarded/reply/media context владельца не включается в delivery
участника; `/shared` также рендерит только reminder text, без context snapshot.
Участники не видят Telegram IDs или identities друг друга: владелец управляет
участниками по непрозрачным membership IDs.

`shared_reminder_memberships`, приглашения и per-recipient delivery metadata
удаляются по bounded retention policy worker-а: истёкшие invite metadata — через
7 дней, отозванные memberships — через 30 дней, delivery rows terminal
occurrence — через 30 дней. Личные reminders и их ownership migration не
изменяются; существующие строки после миграции остаются private.

Production secrets, Telegram/BotFather права, `DEPLOY_ENABLED`, migrations и
production DB writes этим Issue не включаются. Для применения миграции и первой
production доставки требуется отдельный owner-only release gate.
